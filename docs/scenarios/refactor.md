# Scenario: Refactor

## When to use this

You're changing the structure of code without changing what it does:

- Extracting a rate-limit counter that two endpoints duplicate.
- Splitting a 600-line component into smaller ones.
- Breaking up a `utils` module that became a dumping ground.
- Replacing a hand-rolled utility with a library the project has standardized on.

**Not this scenario:**

- Anyone could tell something changed — a reader, a caller, an editor → it's a behavior change: a [change request](change-request.md) on delivered work, or a new spec.
- Fixing a bug, even toward "correct" behavior → [Debugging](debugging.md).
- "While I'm in here, I'll also add…" → stop. Two branches, two pull requests, refactor first.

## The rule

The tests are the contract, and a refactor doesn't change the contract: **tests stay green
throughout, and their assertions don't change.** A test that needs a different assertion is telling
you the behavior changed. The one exception is mechanical — an import path that moved — and the
commit body says so.

## Does it need a spec?

The same test as everything else: **is there anything to decide?**

| Refactor | Spec folder |
|---|---|
| Mechanical, inside the existing design — extract a helper, rename, split a file, remove dead code | None: `/refactor` → `/commit` |
| A structural decision — a new layer or module boundary, a pattern other code must follow, a library replaced, shared code with many consumers reshaped | Yes. `spec.md` is short: why, and that behavior doesn't change. `plan.md` carries the decision, the rejected alternatives, and the **change surface** — the part most likely to be wrong. Tasks are `refactor:` commits. Same approval gate |
| …and the decision should outlive the change ("all CMS reads go through one module", "rate limiting uses library X") | Also an **ADR** (`/record-decision`) in the same pull request, linked from the spec's `references.adrs` |

Replacing a library is never "nothing to decide": the new dependency is justified in `plan.md`, the
lockfile is regenerated by the package manager (the `protect-paths` hook blocks hand edits), and the
old library is removed in the same branch.

## Steps

1. **Triage** (`/triage`): deliverable change; kind refactor, no behavior change; environment needed
   — the tests run; spec folder per the table above.

2. **Check the safety net.** Run the tests that cover the area — green before you start. Missing
   coverage? Write characterization tests first and commit them (`test:`). They pass on their first
   run, because they pin what exists — so prove each one can fail: break the behavior on purpose,
   watch it go red, restore it.

3. **`/refactor`** — one change at a time, tests after each. A step that goes red is reverted, not
   patched. Each green step that stands on its own is a commit (`refactor:`).

4. **No docs-first.** No behavior change means no user-facing docs to write. Docs that describe the
   structure — `docs/reference/` pages, `docs/ARCHITECTURE.md` — are updated in the same branch
   (`docs:`). Wanting to change an admin guide means the behavior changed.

5. **`/review`**, with refactor questions: is the public behavior identical? Is the code simpler, or
   did the complexity move? Does every consumer of the shared code still work? Is there a pattern the
   project doesn't use elsewhere?

6. **Deliver** — once the full gate and `/review` pass, a draft pull request that's boring to review; a refactor has nothing new to try locally. If a reviewer has to ask
   "did this change behavior?", it does too much.

## Example

The newsletter's rate limiter (`lib/newsletter/rate-limit.ts`) and the contact form's spam check
(`lib/contact/spam-check.ts`) are two copies of one fixed-window counter on the shared Redis store.
The newsletter's plan kept them apart on purpose — merging them wasn't asked for and would have
changed the contact form in that pull request. A comment form is next, which would make three copies.

**Triage:** change; refactor, no behavior change; environment needed for the tests; spec folder
none — a shared helper inside the existing structure has nothing to decide.

**Safety net.** The newsletter's tests pin its limit and its 60-second expiry, but nothing pins the
contact form's: 3 messages per IP per 10 minutes. A characterization test does — "blocks the fourth
message from one IP within 10 minutes" — green on its first run, red when the limit is changed on
purpose, green again when restored.

**The goal and the steps**, stated before the first change (`/refactor`):

```
Goal: one fixed-window counter, so the comment form doesn't add a third copy.
1. Extract lib/rate-limit/fixed-window.ts — hit(key, limit, windowSeconds) — from the newsletter's
   limiter, which keeps its key prefix, its limit, and its window.
2. Move the contact form's spam check to it, passing its own prefix, 3 requests, and 600 seconds.
Full suite green after each step; no assertion changes; each step is a commit.
```

The contact form's 10-minute window looks arbitrary next to the newsletter's minute, but deciding
the right value isn't a refactor's job: it's preserved, and the question goes to the contact form's
owner as a follow-up.

**A version with something to decide.** Later the team wants one content service to own every CMS
read — client, preview mode, error mapping — instead of each adapter doing its own. That's a new
boundary other code must follow, so it gets a spec folder (`specs/012-content-service/`, branch
`refactor/content-service`). Its `spec.md` states the requirement that matters — behavior unchanged:
the existing suite passes with no assertion changes, and no module outside the service imports the
CMS client. Its `plan.md` change surface lists every adapter, page, and route that reads the CMS.
It goes through the gate, and an ADR records the boundary.

## Common mistakes

| Mistake | What happens | Instead |
|---|---|---|
| Refactor and feature in one branch | Reviewers can't separate structure from behavior; bugs hide in the diff | Two branches; the refactor lands first |
| Refactoring untested code | "I think it still works" | Characterization tests first, each proven able to fail |
| Changing assertions "to clean the tests up" | The contract you're preserving moves with the code | Tests stay as they are; test cleanup is its own refactor |
| Fixing what you find along the way — that 10-minute window | A behavior change ships labeled `refactor:` | Preserve it; raise it with the owner |
| Abstracting for the future | More indirection today for a need that may never come | Extract for what exists — two or three real uses |
| Treating a structural decision as mechanical | Nobody checks the change surface; the next feature ignores the new boundary | Something to decide → spec folder, gate, maybe an ADR |
| Hand-editing the lockfile when swapping a library | The hook blocks it, or the lockfile drifts from the manifest | Let the package manager regenerate it |
